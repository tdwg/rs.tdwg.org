# BDQ release inputs

Inputs for processing the Biodiversity Data Quality (BDQ) standard for the public review at `bdq-public-review.rs.tdwg.org` ([tdwg/bdq#340](https://github.com/tdwg/bdq/issues/340); plan: [`tg2/_make_review/deployment_rs_tdwg_org.md`](https://github.com/tdwg/bdq/blob/master/tg2/_make_review/deployment_rs_tdwg_org.md), Section 8).

The BDQ release is a sequence of releases, one directory per date (plan Section 8.5). Each term's first version on bdq-public-review.rs.tdwg.org is dated when its current content last changed in the BDQ draft. In the draft, these versions are placeholders (that happen to reflect the terms' history); on ratification they become real term versions with the release date. The draft releases, `bdq-revisions-2024-04-13/` to `bdq-revisions-2026-05-16/`, each add the terms whose content dates from that day; `bdq-revisions-2026-11-09/` holds the decided `bdqffdq` changes (plan Section 9.5). `bdq-revisions-2026-11-12/` holds the new definitions of the `bdqval` terms `AllValidationTestsRunOnSingleRecord` and `AllAmendmentTestsRunOnSingleRecord` (plan Section 10.9.7), the first release edited directly in this repository rather than converted from tdwg/bdq. The vocabularies are the five simple vocabularies (`bdqdim`, `bdqenh`, `bdqcrit`, `bdquc`, `bdqval`) and the Fitness For Use Framework ontology (`bdqffdq`). Each release directory holds:

- `config.yaml`: the release declaration (standard, vocabularies, namespaces, List of Terms documents);
- `<prefix>.csv`: one release-input CSV per namespace declared in the release, with the terms new or changed on that date (header only if none);
- `mappings/<dataset>/`: in the release that creates a term list, and where they change, the BDQ column mapping files and `namespace.csv` for each dataset. They follow BDQ's own RDF (plan Section 8.3).
- `bdqffdq-axioms.ttl` (in the releases where the axioms change: the faithful axioms in 2024-10-01, a release of their own, dated by their history in tdwg/bdq (the axioms of `bdqffdq.owl` last changed on 2024-10-01, commit `8005faba`, before the decided changes), and the decided axioms in 2026-11-09): the statements about `bdqffdq` terms that cannot be rows of `bdqffdq.csv` (restrictions and other axioms with blank nodes). They are the vocabulary extension term list `https://rs.tdwg.org/bdqffdq/extension/` (TDWG Standards Documentation Specification, Section 4.4.2.2), declared under `extension_lists` in `config.yaml` from 2024-10-01 on and processed by `process.py`. The list gets a new version whenever its axioms or one of its member terms change (see `../process-ontology.md`, Section 4; plan Section 9.6). To change the axioms, add a release with the edited axioms file (`../process-ontology.md`, Section 5).

Together, these files were generated from `tg2/_review/vocabulary/*_term_versions.csv`, `tg2/_review/vocabulary/bdqffdq.owl`, and the List of Terms `document_configuration.yaml` files in [tdwg/bdq](https://github.com/tdwg/bdq).

They were generated by `bdq_to_rs.py` (from tdwg/bdq master `10a5d682`):

```bash
python -I bdq-revisions/bdq_to_rs.py <path to tdwg/bdq> <path to rs.tdwg.org> 2026-11-09
```

The `bdqffdq` inputs were generated by `bdqffdq_to_rs.py` (from tdwg/bdq master `dcaf80dd`; since `3350a4ea`, tdwg/bdq's `bdqffdq.owl` is the ontology generated here, so a rerun needs the earlier draft file), which checks that the term list and the axioms together reproduce `bdqffdq.owl`, apart from documented differences:

```bash
python -I bdq-revisions/bdqffdq_to_rs.py <path to tdwg/bdq> <path to rs.tdwg.org> 2026-11-09
```

The converters wrote a single release; `bdq_split_by_date.py` then split it into the sequence, taking each term's draft date from `issued` in the BDQ term-version files and `dcterms:issued` in the draft `bdqffdq.owl` (tdwg/bdq `4aff59f0`; `bdqffdq:aggregatesResponsesFrom` has no date there and gets 2026-04-23, when it was added). The `bdqffdq` rows of the draft releases are the faithful conversion (`e229ed37`); `bdq-revisions-2026-11-09/` holds the 7 rows that the decided changes alter.

The BDQ documents other than the Lists of Terms (the ontology, Vocabulary Extension, guides, Quick Reference Guide, supplement, and tutorial; plan Section 11) were added to the `documents` of `bdq-revisions-2026-11-09/config.yaml` by `bdq_docs_to_rs.py` (from tdwg/bdq master `097a86ad`), with the document IRIs decided in plan Section 11.3. On the review site each has only its latest version, so they are declared only in the last release:

```bash
python -I bdq-revisions/bdq_docs_to_rs.py <path to tdwg/bdq> bdq-revisions/bdq-revisions-2026-11-09/config.yaml
```

`bdq_to_rs.py`, `bdqffdq_to_rs.py`, `bdq_split_by_date.py`, and `bdq_docs_to_rs.py` are for the public review only. They bootstrap these inputs from the files in tdwg/bdq, and are intended to be replaced by authoritative information kept in this repository: from now on, the files in the release directory are the source and are edited directly. Rerunning the scripts overwrites them.

## Processing

Process the releases in date order, from the `process` directory. After each release, copy that release's BDQ mapping files into the dataset directories; `process.py` creates a new term list's mapping files from the templates, and the BDQ files replace them. The axioms file is handled by `process.py`:

```bash
for d in $(ls -d bdq-revisions/bdq-revisions-20* | sort); do
  python process.py --config $d/config.yaml || break
  if [ -d $d/mappings ]; then (cd $d/mappings && for m in */; do cp "$m"* "../../../../$m"; done); fi
done
```

Use `--dry-run` first to check a release. For the extension term list, `process.py` writes the current axioms (`bdqffdq/bdqffdq-axioms.{ttl,rdf,jsonld}`) and an immutable copy per version (`bdqffdq/axioms-versions/`), and records the list, its versions, members, and distributions in `term-lists/` and `term-lists-versions/`. The distributions' access URLs point to the `bdq` branch (`distribution_base_url` in `config.yaml`).

Each release's `config.yaml` sets `new_term_list: true` only for the term lists that the release creates. A release can be rerun on the same date (for example the last one, after correcting its inputs); for an earlier release, rebuild from the first release, because each later release depends on it.
